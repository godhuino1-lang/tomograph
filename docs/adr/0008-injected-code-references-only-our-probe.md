# 8. 插桩模块注入的字节码，只引用我们自己的探针

- 状态：已接受
- 日期：2026-10
- 相关：[ADR 0006](0006-langchain4j-cut-points.md)（切点选择）、[ADR 0007](0007-modules-are-application-plugins.md)（模块是应用插件）

## 背景

模块要采集的是**框架对象里的数据**：请求的模型名与参数、响应的 token 数与结束原因。

直觉做法：让注入的字节码直接调用框架的 getter——
`ALOAD request; INVOKEVIRTUAL dev/langchain4j/model/chat/request/ChatRequest.modelName()Ljava/lang/String;`
——然后把它交给我们的探针。

这会带来一个具体的风险：**注入的指令里出现了框架的类型**。于是"框架升级"这件事，从"我们的属性读不到"升级成了"宿主的字节码链接失败"。

## 决策

**注入的字节码只引用我们自己的探针类；框架对象一律以 `Object` 传递；字段提取在探针里用反射完成。**

```
注入：LDC "doChat(...)..."; ALOAD 0; ALOAD 1; DUP(response); INVOKESTATIC <我们的探针>(Ljava/lang/String;Ljava/lang/Object;Ljava/lang/Object;Ljava/lang/Object;)V
                        ↑ 全是 JDK 类型和我们自己的类型
```

## 三条理由

1. **链接风险归零。** 注入的指令里没有框架类型，所以框架怎么改都不会在宿主里造成 `NoSuchMethodError` 或 `NoClassDefFoundError`。**这是最重要的一条**：本项目的头号纪律是"观测绝不能弄坏宿主"，而链接错误正是最难排查的那类弄坏方式（它出现在一个与观测毫无关系的调用点上）。
2. **模块因此不需要编译期依赖框架。** 这不是巧合而是收益：它让模块能在**没有 jar** 的环境里编译、单元测试通过——也就是本项目的现实情况。一个必须等 jar 才能写一行代码的模块，会让整个 v0.1 卡在一个下载动作上。
3. **提取可以"尽力而为"。** 读不到某个字段就是少一个属性；而不是抛异常、也不是整个 span 消失。

## 代价（写下来，不掩盖）

| 代价 | 应对 |
|---|---|
| 反射开销 | 每次**模型调用**一次。相对一次 LLM 调用（几十到几千毫秒）可忽略，但要在 JMH 里计入插桩开销 |
| 访问器名字可能随版本变化 | 每个属性用**候选名字列表**按序尝试；**核实过的名字排在最前**，并标注核实到哪个版本 |
| **属性缺失是静默的** | 这是真实代价：反射读不到不会报错。**只能由针对真实版本的集成测试发现**——所以"每个受支持版本都有集成测试"不是一句口号，它是这个设计的必要配套 |
| 反射在模块化/受限环境下可能被拒绝 | 探针必须捕获 `Throwable` 并降级（见下） |

## 给未来模块作者的约束

1. 注入的调用**描述符里只能出现 JDK 类型和我们自己的类型**。想传框架对象？用 `Object`。
2. 探针方法**绝不抛异常**。它运行在宿主的方法调用路径上。
3. 候选名字列表要**标注来源**：哪个是核实过的、核实到哪个版本、哪些是推测的。
4. 如果一个属性只对某个版本有效，**写在代码注释里**，别让它变成"某天突然没人知道为什么读不到"。

## 复核方式

- 单元测试用**复刻框架形状的假类**（同样的方法名、同样的返回类型），验证提取逻辑与降级路径——不需要 jar。
- 针对**真实 jar** 的集成测试属于 v0.1 验收：它验证的是"候选名字里第一个是对的"，这件事只有真 jar 能回答。
