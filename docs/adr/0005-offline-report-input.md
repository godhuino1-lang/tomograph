# 5. 离线报告的输入格式，以及"零依赖"这条规矩到哪里为止

- 状态：已接受
- 日期：2026-10
- 相关：ADR 0003（零依赖 OTLP 导出）

## 背景

v0.2 要交付一个**单文件、可离线打开的 HTML 报告**（[SCOPE.md](../../SCOPE.md) 里明确保留的唯一 UI 例外）。

它需要**读回**已采集的数据。而我们有两份互不相同的数据形态：

1. **内部模型**（`TomographSpan`）——agent 采集时用的。
2. **OTLP/JSON**——导出到后端用的，是一个**由别人固定的外部格式**。

同时 [ADR 0003](0003-zero-dependency-otlp.md) 立了一条硬规矩：**零第三方依赖**。于是问题变成——这条规矩是否也管报告模块？如果管，我就得**手写一个 JSON 解析器**。

## 决定

### 1. 报告读 **OTLP/JSON**，不读内部模型

**理由**：如果报告依赖内部模型，那么"只有采集这批数据的那次构建才能渲染它"——而离线报告的全部意义，正是**两年后把一份文件附到 bug 报告里还能打开**。依赖一个会随版本变化的内部结构，就破坏了这个前提。

附带的好处：**任何会说 OTLP/JSON 的工具产出的数据都能渲染**，我们不必为此写代码。

### 2. 报告模块**可以**用第三方库（当前是 Jackson）

**理由**：ADR 0003 的论证**逐条不成立**于离线工具：

| ADR 0003 的理由 | 对 agent | 对离线报告 |
|---|---|---|
| shaded 进来的库会和宿主自己的副本**版本冲突** | 成立（我们在别人的 JVM 里） | 不成立（独立进程，自己的 classpath） |
| 每个开启插桩的应用都要**多付 jar 体积和类加载代价** | 成立 | 不成立（不在任何应用的启动路径上） |
| 依赖库的漏洞面暴露在**生产进程**里 | 成立 | 不成立（开发者的机器） |

**手写一个 JSON 解析器去遵守一条不适用的规矩，是错误的"一致性"。** 真正的一致性在于：**规矩的目的**（不干扰宿主）在哪里成立，它就在哪里生效。

### 3. agent 仍然**零第三方依赖**，并且这条要能被机器检查

这条界线很容易被无意中越过：今天在报告模块里加一个库没问题，明天有人为了复用把报告模块加进 agent 的依赖树，ADR 0003 就被悄悄推翻了。

**因此需要一个 CI 检查**：`tomograph-javaagent` 的依赖树里**不允许出现任何第三方 artifact**（只允许本仓库自己的模块 + JDK）。

> 待办：用 `maven-enforcer-plugin` 的 `bannedDependencies` 规则实现，或在 CI 里解析 `mvn dependency:tree`。**目前还没做**——这条纪律现在只写在文档里，而写在文档里的纪律会被违反。

## 后果

- 报告是**文件 → 文件**的纯函数，不需要 agent、不需要网络、不需要被观测的应用在场。
- 读取层必须自己处理 proto3 JSON 的怪癖（64 位整数是字符串、`AnyValue` 是带标签的联合体、字段缺失与空值不同）。这些都已经在 `OtlpJsonReaderTest` 里用**真实抓到的 payload** 钉住了。
- **不完整的数据必须被显式标注**：parent 不在文件里的 span 会被渲染成顶层节点，**同时被计数**（`SpanTree.orphanCount()`）。把一次不完整的录制当成完整呈现，会让"agent 少跑了几步"看起来像真的。
- 模块边界上多了一条需要守的线：**报告可以胖，agent 必须瘦。**
