# ADR 0001 — Java 基线定为 17，不是 8 或 11

- 状态：已接受
- 日期：2026-10
- 决策者：项目作者

## 背景

初始技术方案里写的兼容矩阵是 `JDK 8 / 11 / 17 / 21`。这个矩阵看起来"覆盖更广 = 更厉害"，但它是错的。

## 决策

**基线 = Java 17**，兼容矩阵 = **17 / 21 / 25**（三个 LTS）。本地开发用更新的 JDK（当前 26），通过 `maven.compiler.release=17` 交叉编译降级。

## 理由

1. **矩阵必须跟着宿主应用走，而不是跟着"能支持多少"走。** Tomograph 插桩的对象是 Java 写的 LLM Agent 应用，而这类应用的主流产框架有硬性 JDK 要求：

   - **LangChain4j 要求 Java 17+**
   - **Spring AI 要求 Java 17+**

   也就是说，**不存在**一个跑在 JDK 8 或 11 上的宿主应用等着被我们观测。支持它们是零收益的负担：为 JDK 8 编译意味着放弃 `record`、`var`、`switch` 表达式、`List.of`、`sealed`，代码质量会明显下降，换来的是"支持了一个永远不会出现的用户"。

2. **JDK 8 和 11 都已过常规支持期。** 为一个观测工具维护两个已 EOL 的字节码目标，是把维护预算花在错误的地方。

3. **面试上这么解释反而加分。** "为什么不做 JDK 8？因为宿主框架本身要求 17+，支持 8 是没有用户的成本"——这展示的是**工程判断力**，而不是"能写更多兼容代码"。面试官更想听前者。

## 后果

### 正面

- 可以用 Java 17 的语言特性写 agent 代码（`record` 承载 span 模型、`sealed` 描述插桩结果、文本块写测试 fixture）
- CI 矩阵从 8 个组合（4 版本 × 2 OS）降到 6 个（3 版本 × 2 OS），跑得更快、失败更好定位
- 后续引入 ASM 时只需考虑 17/21/25 三个 class file 版本（61/65/69）

### 负面 / 需要接受的代价

- 如果将来出现"必须观测一个 JDK 11 上的 Agent 应用"的真实需求，需要一次较大重构。**当前判断：这个需求不会出现**；若出现，届时再单开 ADR。
- 本机 JDK 26 比目标基线新两个大版本，存在"本地能跑、CI 上 17 编译失败"的可能。**应对：CI 的 17 号任务就是这条防线的守卫**，本地编译务必带 `--release` 而非 `-source/-target`。
